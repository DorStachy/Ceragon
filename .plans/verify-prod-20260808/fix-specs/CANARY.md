## Cluster-wide mechanism

ONE mechanism, five stacked dead links — and the finding's two hypotheses are only half right. (a) "Never scheduled" is CONFIRMED but for a sharper reason than "there is no scheduler": there IS a 60s jittered full sweep (controller.go:277-316), and the canary is simply not on it. `p.Canary` has exactly one call site (controller.go:665) inside `runCanaries`, whose only caller is `verifyAndResolve` (controller.go:571), whose only callers are the post-repair path (controller.go:545) and the open-episode path (controller.go:565). A target that MATCHES with no open episode returns at controller.go:553-562 having run nothing. The canary is therefore a REPAIR-VERIFICATION GATE, not a continuous-assurance mechanism — it can only ever run on an endpoint whose config was tampered with. On a healthy fleet it is unreachable by construction. Every canary test in the tree drives synthetic drift first (controller_canary_gate_test.go:56-58 "Make the target genuinely drift so repair + verify actually run"), which is why the suite is green over a path production never enters. (b) "Backend exposes NO canary route" is DISPROVEN. Three exist and are mounted: `POST /api/v1/ai/policy-delivery/canary` (mint, endpoint-control-authority.controller.ts:592), `POST .../control-artifact/consume` (redeem, :633), `GET .../canary-rollup` (fleet read, :247) — and a console panel already consumes the rollup (Frontend app/admin/endpoints/ai-canary-fleet-panel.tsx, mounted at coverage-section.tsx:1162) with the same honest never-run copy. The probes in FINDINGS.md hit invented paths. What is genuinely missing server-side is a PER-INSTANCE proof surface: no receipt route/storage, and the protection-depth DTO never projects the per-instance integrity block (documented in Frontend types/ai-governance.ts:2936-2942 as "OPEN SEAM (2026-07-29)"). Even if the schedule were fixed today, four more links are dead and each independently guarantees a non-PROVEN outcome: the requested proof kind is one NEITHER host invoker can drive; the codex applied-bundle binding is never populated so every codex canary fails a binding check; no ReceiptSink implementation exists anywhere in Installers so a codex PROVEN degrades to ERROR by design; and the console projection drops the field. Fixing only the schedule would move the fleet from "never run" to "ran and errored" — a worse-looking, equally uninformative state. All five must land together. The safety design is the good news: the probe machinery is already the strongest part of this codebase (fixed deny-only token, closed proof-kind vocabulary, empty temp workdir, closed stdin, bounded output/timeout, SYSTEM-exec privilege gate with de-elevation, hash-only receipts, and a deny that short-circuits BEFORE any event emission so incident counts are already clean). What the schedule newly requires is a COST bound (an unblocked probe reaches the vendor model on the customer's account) and an audit-trail marker on the hook-fire counter.

## F38 - The deny-canary is a repair-verification gate, not a schedule — plus four more dead links; make it run per instance on a cadence and land per-instance proofs in the console

- **Severity**: HIGH - HIGH, not CRITICAL: this is an ASSURANCE failure, not a live enforcement failure. Blocks were proven to work manually on the same endpoint (PL/CC-1), and local-authoritative enforcement is unaffected. What is dead is the product's own continuous self-attestation — the mechanism that is supposed to tell a customer, unprompted, that the thing they bought is still firing. Its absence is invisible by design: every surface reports it honestly, so nobody is misled today, which is what keeps it off CRITICAL. But it means an endpoint whose hook silently stops enforcing (a runtime upgrade outside the supported dialect, a de-elevation refusal, a foreign administrator's settings winning) would be discovered only by a human running a manual test, and the product's central claim — 'author policy, it enforces' — has no automated proof anywhere in the fleet.
- **Side**: multi   **Effort**: XL   **Root cause verdict**: REVISED

### Root cause

FIVE independent blockers, each sufficient on its own; the finding names one of them and gets the second wrong.

B1 — NOT SCHEDULED (the primary, and the one the finding got right, though for a sharper reason). A scheduler exists: Controller.Run drives a 60s ± 10s jittered full semantic sweep (Installers internal/airuntimeintegrity/controller.go:277-316, SweepInterval :46). The canary is not on it. `p.Canary` has exactly ONE call site (controller.go:665) inside `runCanaries` (:659); `runCanaries` has exactly ONE caller, `verifyAndResolve` (:571); `verifyAndResolve` has exactly TWO callers, the post-repair path (:545) and the open-episode path (:565). `reconcileTarget` routes a non-drifted target to `onEffectiveMatch` (:483), which for `rec.ActiveEpisodeID == ""` sets StateMatched and RETURNS (:550-562) — no canary. So a canary can only fire on a target whose config was tampered with and repaired. On a healthy endpoint the whole lane is unreachable by construction, which is exactly what the live endpoint measured: 17 targets reconciled, lastCanaryAt=(none) everywhere.

B2 — THE REQUESTED PROOF KIND CANNOT BE DRIVEN BY EITHER HOST. The daemon asks the Backend for `DENY_TOOL_FIXED_PROBE` (internal/daemon/ai_canary_challenges.go:58), with a comment claiming the pre-tool checkpoint is "the one checkpoint BOTH managed runtimes expose" (:50-57). The code says the opposite: claude's ExecHostInvoker returns `Unsupported` for anything but `DENY_PROMPT_FIXED_PROBE` (providers/claude/canary_host.go:58 + :105-107) and codex's ExecCanaryHost returns `Synthetic` for the same reason (internal/codexmanaged/canary_host.go:250 + :136-139), each with an explicit comment that the tool/escalation probes need the MODEL to choose a tool call and cannot be made deterministic. So even with a perfect challenge, every probe on every endpoint resolves to CanaryUnsupported. Nothing pins the requested constant against the drivable one.

B3 — THE CODEX APPLIED-BUNDLE BINDING IS NEVER POPULATED. Production wiring sets only `w.codex.Canaries.Applied.EndpointID` (internal/daemon/ai_integrity_wiring.go:588). RunCanary compares the challenge's appliedBundleRevision/Digest/ProjectionHash UNCONDITIONALLY against `cfg.Applied.*` (internal/codexmanaged/canary.go:301-306) — and the Backend ALWAYS populates those three fields in the minted payload (endpoint-control-authority.service.ts:266-268; they are required by the shape gate). Non-empty vs "" ⇒ `canary-challenge-wrong-bundle` ⇒ CanaryError on every codex canary, before the host is ever launched. The claude lane escapes only because it guards each comparison with a non-empty check (providers/claude/canary.go:278-286) — which means the claude lane performs NO applied-bundle binding at all in production, a security asymmetry worth closing in the same change.

B4 — NO ReceiptSink IMPLEMENTATION EXISTS. `codexmanaged.ReceiptSink` / `claude.ReceiptSink` are interfaces with zero implementations in the whole Installers tree (grep for `UploadCanaryReceipt` returns only the interface at codexmanaged/canary.go:172 and its two call sites). `Receipts` is never assigned in the daemon. codexmanaged/canary.go:379-387 then deliberately degrades a genuine PROVEN denial to CanaryError/`canary-receipt-upload-failed`, because "the proof is the denial PLUS the correlated receipt". So the codex lane cannot produce PROVEN even in principle.

B5 — THE PER-INSTANCE PROOF HAS NO CONSOLE PROJECTION. The wire contract already carries it: `RuntimeInstanceIntegrity.enforcementTestedAt/proofExpiresAt/lastCanaryAt` on the heartbeat's runtimeAdapters (Installers internal/controls/attestation.go:619-632), ingested and normalized by Backend src/ai-governance/runtime-adapter-shape.ts:169-180 + :640-650. But nothing on the endpoint ever WRITES them (both producers of `airuntimeinventory.GovernanceEvidence` populate only ActiveTamper; ai_integrity_observed_projection.go deliberately copies only controlTargetKey + observedProjectionHash, :30-63), and server-side the render projection carries lastCanaryAt/proofExpiresAt but drops enforcementTestedAt (runtime-adapter-render.util.ts:435-437 vs :1190-1191). The Frontend already documents the resulting hole: "OPEN SEAM (2026-07-29): AiProtectionDepthAdapterDto does NOT carry this member yet" (Frontend types/ai-governance.ts:2936-2942), so protection-depth.tsx:1078-1093 renders its 'not served for this adapter' block unconditionally.

WHAT IS *NOT* BROKEN, contrary to the writeup: the Backend has three working canary routes (endpoint-control-authority.controller.ts:247/:592/:633), a fleet rollup whose `everRun` is honestly derived from consumption alone (endpoint-control-authority.service.ts:96-116), and a shipped console panel consuming it (Frontend app/admin/endpoints/ai-canary-fleet-panel.tsx via coverage-section.tsx:1162). The 404s in FINDINGS.md are wrong paths. The Backend 409 gate (`AI_CANARY_NO_APPLIED_BUNDLE`, service.ts:236-248, and the per-instance projection-hash 409 at :249-254) is CORRECT and must stay; the endpoint side of it was already closed by ai_integrity_observed_projection.go, and the live evidence shows this endpoint activating signed bundles normally (rev 6→7→8 ENFORCE with receipts), so B1-B5 — not the 409 — are what keeps the fleet at zero.

### Fix

Turn the canary from a repair-verification gate into a scheduled per-instance assurance loop, and open the two links that carry its verdict to the console. Five agent changes + one backend route/storage + one projection, all of which must land together because each of B1-B5 independently forces a non-PROVEN outcome.

1. SCHEDULE (closes B1). A pure, exhaustively-testable due predicate in airuntimeintegrity, driven from the sweep that already runs:
   - no InstanceRecord ⇒ due (first proof)
   - persisted RuntimeVersion != the binding's current RuntimeVersion ⇒ due (a proof only covers the version that produced it)
   - PROVEN ⇒ due at ProofExpiresAt − CanaryRefreshLead (4h before the 24h CanaryProofLifetime lapses)
   - NOT_PROVEN / ERROR / UNSUPPORTED ⇒ due at ObservedAt + CanaryRetryInterval (6h)
   - unparsable stamp ⇒ due (an unreadable stamp is not a fresh proof)
   The 6h floor after NOT_PROVEN is the load-bearing safety rule, not a nicety: an unblocked probe is the one case that reaches the vendor model on the customer's account, so a broken hook must make the canary SLOWER, never faster. `onEffectiveMatch`'s steady-state branch calls the same `runCanaries` (no second copy of the persist/redeem logic), capped at 2 probes per sweep. The due filter lives INSIDE `runCanaries` so both entry paths obey it; in exchange `verifyAndResolve` must compute `blocking` from the PERSISTED record when no fresh run happened (any required instance whose latest outcome is NOT_PROVEN still blocks) and must release containment only when every required instance holds an unexpired PROVEN record — otherwise deferring a probe would silently resolve an open gap.
   The acquisition loop inherits the same predicate: RefreshCanaryChallenges mints only for DUE instances, which also stops the current behaviour of minting an unused 5-minute challenge every ~15 minutes per instance and inflating the rollup's issued/consumed ratio.

2. PROOF KIND (closes B2). Export the drivable kind from each provider and derive the requested one from it, so the two can never drift again: `codexmanaged.DrivableCanaryProofKind` and `claudeprovider.DrivableCanaryProofKind` (renames of the existing unexported constants), `requestedCanaryProofKind = claudeprovider.DrivableCanaryProofKind`, plus a test asserting the two providers agree and that the value is a member of endpointcontrolauth.CanaryProofKinds. Rewrite the comment at ai_canary_challenges.go:49-58, which currently justifies the wrong choice.

3. APPLIED BINDING (closes B3). Populate the full AppliedBinding for BOTH providers from the same facts the heartbeat reports — bundle revision/digest from the RA-2 snapshot (already assembled at ai_integrity_subsystem.go:378-388), projection hash from the controller's TargetRecord for the governing target — refreshed per sweep in BoundInstances alongside the other provider fields. Make the claude comparisons unconditional too, so both lanes bind identically.

4. RECEIPT LANE (closes B4). Implement ReceiptSink over a new signed endpoint route and wire it into both providers. Consumption stays where it is (the controller's CanaryConsumer, after persistence) — receipt and redeem are two different facts and ai_canary_consumption.go:20-24 already insists on keeping them apart.

5. CARRY + PROJECT (closes B5). Stamp the controller's per-INSTANCE record onto the inventory rows at the single existing carry point, and project the integrity block onto the protection-depth DTO — with `enforcementTestedAt` derived SERVER-SIDE from the consumed receipt row, never from the endpoint's self-report, which is exactly what the console hint already promises.

SAFETY DESIGN — what a safe probe is, on a customer machine (the hard part, and mostly already correct; the schedule is what makes it load-bearing):
  S1 CONTENT. The probe is a fixed DeVoid-namespaced token plus one opaque correlation id plus 'this is an automated DeVoid enforcement self-test. Take no action and produce no output.' No path, no credential, no user content, no free-form field anywhere in the request surface (probe.go:38-69). UNCHANGED.
  S2 SURFACE. The entire request vocabulary is CanaryProofKinds, every member a DENY. There is no allow, no weaken, no command. A forged or replayed challenge can only ever ask the host to refuse something. UNCHANGED.
  S3 HARMLESS IF IT SUCCEEDS. The worst case is one model turn on a prompt whose only instruction is to do nothing. It cannot touch customer data: the child runs in a FRESH EMPTY temp directory created per probe and deleted after (claude canary_host.go:213-222; codex `-C dir`), with stdin closed to an empty reader (exec.go:118) so nothing is piped in, and codex additionally runs `--sandbox read-only`. The claude lane has no equivalent sandbox flag today — the implementer must check `claude --help` on the pinned 2.1.x family for a tool-disabling flag and pass it if one exists; if none does, the empty workdir stays the bound and that limitation is recorded in the doc comment. Do not invent a flag.
  S4 COST/RATE. At most one probe per runtime instance per due interval (≥6h, normally ~20h); at most 2 probes per 60s sweep; at most 4 challenge acquisitions per 2-minute tick (already bounded). A NOT_PROVEN lengthens the interval. This is what keeps a fleet-wide hook regression from turning into a fleet-wide vendor-API bill.
  S5 PRIVILEGE. An elevated daemon never executes a binary a standard user can rewrite with its own token: it de-elevates into the owning interactive user or refuses with a closed reason code (guard.go:246-278). The schedule makes this gate fire routinely for the first time, so `canary-host-*` refusal slugs will start appearing in the field — they are honest results and the console must render them as 'could not measure', never as a gap.
  S6 EDR. Fixed literal argv, no shell, no interpreter, no encoded arguments, no DeVoid-originated network from the child; the process is the vendor's own installed binary, started by the interactive user after de-elevation, bounded at 60s with a forced pipe teardown. Nothing in the tree resembles LOLBin behaviour. ONE residual: on Windows npm layouts the host is `codex.cmd`/`claude.cmd`, which Go resolves through the command processor, so an EDR may observe `cmd.exe /c codex.cmd`; prefer a sibling `.exe` when the RA-3 inventory found one, keep the `.cmd` otherwise (refusing would kill coverage on the commonest layout), and document it. The probe token is a stable, greppable marker — publish it in the ops docs as the canary's signature so a customer can allowlist the behaviour instead of investigating it.
  S7 AUDIT-TRAIL SEPARATION. The probe deny is produced before the scanner, before the policy, and before any backend report, and returns immediately (ai_handlers.go:1104-1131) — no ai_event, no TOOL_CALL_BLOCKED, no session event, no bypass telemetry. Incident counts are already clean and a regression test must pin that. The canary's only records are the local InstanceRecord, the receipt row and the consumed authority row, all in the control-authority lane, all carrying `integrity-canary-deny-probe`, none in the incident tables. The ONE real pollution today is ai_handlers.go:1101, which counts the probe as a fired user turn on the UserPromptSubmit checkpoint; record it under a self-test marker so operator-facing fire counts separate a customer turn from a self-test.
  S8 NO CONFUSION WITH A REAL BLOCK. The token is long, uppercase and DeVoid-namespaced so it cannot collide with developer prose, and matching it anywhere in the text can only ever produce a DENY (probe.go:71-80).
  S9 PRIVACY. Receipts are identifiers, hashes, enums and RFC3339 stamps only; executable paths and config roots are local-only and never reach a receipt, a log or the wire. UNCHANGED.

CONSOLE — what it should show, with the CLI copy preserved verbatim. Per instance, four states that must stay distinguishable: PROVEN (with observed-at and expires-at, and the note that it was set by a server-consumed receipt); NOT PROVEN — 'the probe ran on this instance and was not refused: a measured enforcement gap'; NOT MEASURED — 'no canary has run on this instance yet. This is a measured absence, not a pass: nothing here has been shown to enforce.' (the CLI's sentence, reused word for word); COULD NOT MEASURE — with the closed reason slug. The fleet panel keeps its existing never-run empty state and its no-percentage-over-a-zero-denominator rule, and gains the per-instance rollup (proven / measured gap / never measured / could not measure) as counts. Nothing here may render an absence as calm and nothing may render UNSUPPORTED or ERROR as a gap.

### Risks

OLD AGENT → NEW BACKEND: an agent that never sends canaryOutcome/canaryReasonSlug leaves them absent; the normalizer must treat absence as 'never reported' and the console must render NOT MEASURED, not a gap. The new receipt route simply receives nothing from old agents and the new proof columns stay NULL — a real state, not an error.
NEW AGENT → OLD BACKEND: the two new integrity fields are additive/omitempty and an old normalizer drops unknown keys; the receipt POST 404s, which the provider already treats as an authoritative refusal and degrades PROVEN to `canary-receipt-upload-failed` — honest, and no worse than today. This is exactly why DEPLOY ORDER IS BACKEND FIRST: ship the route, columns, shape gate and projection, then the agent.
BIGGEST BEHAVIOURAL RISK — enforcement outcomes moving. Setting `Evidence.EnforcementTestedAt` feeds `GovernanceEvidence.hasEnforcementProof()` and therefore `deriveOutcome`, so instances that today report a lesser outcome will begin reporting PROVEN_GOVERNED. That is the correct meaning of the field, but it is a fleet-visible change: it must be gated strictly on Outcome==PROVEN AND an unexpired ProofExpiresAt, and a stale proof must fall back rather than latch. A bug here manufactures green, which is the one failure mode this programme exists to prevent.
SECOND RISK — the opposite direction. Steady-state canaries can now open a CANARY_FAILED episode on a target whose file matches. If the probe classifier has any false-negative mode (a host that refuses in a shape the composite observable does not recognise), the endpoint would manufacture an enforcement gap about itself — codexmanaged/canary_host.go:280-290 records that exact class of bug having shipped once already. Mitigations: NOT_PROVEN never triggers repair (the file matches), only the honest gap; the 6h backoff bounds the noise; containment still requires the repair budget to be exhausted.
THIRD RISK — cost and process noise. Each due probe launches a real vendor CLI. Bounded at ≤2 per sweep and ≥6h per instance, but an endpoint with many instances still sees more child processes than before, and an unblocked probe spends one small model turn on the customer's account. On Windows npm layouts an EDR may observe `cmd.exe /c codex.cmd`. Both are why safety rules S4 and S6 are part of the spec rather than notes.
FOURTH RISK — de-elevation refusals become visible. The privilege gate has effectively never fired in production because the canary never ran; scheduling it will surface `canary-host-executable-untrusted` / `-foreign-writable` / `-no-interactive-session` across the fleet. These are correct security decisions and must render as 'could not measure' with the specific slug — never folded into one code, never rendered as a gap, never softened into UNSUPPORTED without the reason.
FIFTH RISK — challenge volume changes shape. Coupling acquisition to the due predicate REDUCES mint volume (today roughly one unused challenge per instance per 15 minutes), so the fleet rollup's `challengesIssued` will fall while `challengesConsumed` rises for the first time. Expect the ratio to move; that is the fix working, not a regression.
SHARED CONTRACTS: two contract files change and both must be applied to all three mirrors (Backend/packages/shared-contracts, the workspace packages/shared-contracts, Ceragon-Intelligence/packages/shared-contracts) or the intel repo stops building.
