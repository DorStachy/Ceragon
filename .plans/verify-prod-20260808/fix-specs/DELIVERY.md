## Cluster-wide mechanism

ONE MECHANISM UNDERLIES ALL THREE: the agent→backend wire expresses SHAPE but not BOUNDS or IDENTITY, and the backend answers a per-item/per-request problem with a whole-request rejection.

(1) THE MISSING IDENTITY (F2). `ai_events.client_event_id` + the unique partial index `ux_ai_events_endpoint_client_event` (Backend src/entities/ai-event.entity.ts:41-44, migration 1782510000000-AddEndpointEvidenceAndSigning.ts:18,34-35) is a fully-built, hash-covered idempotency key. Every synchronous governance route — /ai/prompt/check, /ai/tool/check — appends through `appendEventForOrg` with clientEventId NULL (ai-agent.controller.ts:935-964). ## F2 - Governance event delivery is lossy and indistinguishable from success: the tool lane has no durable twin and NO synchronous route carries the idempotency key the schema already provides

- **Severity**: HIGH - HIGH, not CRITICAL. Enforcement itself is never weakened - the local decision stands on every failure branch (cross-cutting rule 5 is honoured throughout). What is compromised is the AUDIT RECORD: 26 of 136 governed decisions in one 50-minute window had an unknown delivery state, at least one of which had in fact committed, and the product's own readiness surface reports evidence.durable-delivery=degraded against a required capability. For a security product the audit trail IS the deliverable, and 'we cannot tell a lost block from a recorded one' is a direct hit on it. It falls short of CRITICAL because no block was downgraded and the head-of-line wedge (the path to total evidence loss) is currently latent rather than firing.
- **Side**: multi   **Effort**: L   **Root cause verdict**: REVISED
- **Depends on**: F25

### Root cause

Four mechanisms compose; the writeup names one and a half.

(a) THE CLIENT DEADLINE IS A TOTAL-REQUEST DEADLINE ON A SLOW WRITE. `aiInteractiveTimeout = 1500ms` / `aiInteractiveMaxAttempts = 1` (Installers internal/core/backend/ai_prompt.go:711-712) are consumed by the tool lane at internal/core/backend/ai_tool.go:171-172 through `postAiJSONOnceWithTimeout`, which builds `&http.Client{Timeout: timeout}` (ai_prompt.go:944) - a whole-request deadline covering the server's DB work, not a connect deadline.

(b) THE SERVER SIDE OF THAT ROUTE SERIALISES PER TENANT. `toolCheck` appends via `appendEventForOrg` (Backend src/ai-governance/controllers/ai-agent.controller.ts:935), which takes `pg_advisory_xact_lock` keyed on the ORG before every write (src/ai-governance/services/ai-event.service.ts:2423-2441; key derivation src/ai-governance/ai-chain-lock.ts:39-44). Every AI event for the tenant - prompt, tool, browser, spool batch - queues behind that one lock. 136 tool-checks in 50 minutes plus the prompt and proxy lanes puts the p95 over 1500ms. That is exactly the measured signature: the server committed the row at 16:24:57Z; the client abandoned the response at 16:24:59Z. So the timeout is not merely 'too aggressive' - it is the predicted outcome of putting a chain-locked append inside a 1500ms interactive budget.

(c) NEITHER SIDE CARRIES AN IDEMPOTENCY KEY ON THE SYNCHRONOUS ROUTES - although the column, the unique index and the hash coverage all already exist. `ai_events.client_event_id` (src/entities/ai-event.entity.ts:85-86) with unique partial index `ux_ai_events_endpoint_client_event` (:41-44, created by src/migrations/1782510000000-AddEndpointEvidenceAndSigning.ts:18,34-35) is THE designed dedupe key. Its only writer is the spool ingest (src/ai-governance/services/endpoint-evidence-ingest.service.ts:1061). I grepped every non-spec `clientEventId` call site: no synchronous route sets it. `appendEventForOrg` (ai-event.service.ts:909-989) has no dedupe branch at all - only the batch path does (`repo.findOne({ where: { endpointId, clientEventId } })`, :1152-1171).

(d) THE TOOL LANE HAS NO DURABLE TWIN, AND THE COMMENT SAYS SO. Installers internal/daemon/ai_handlers.go:2754-2762 explicitly records the hole ('unlike the prompt lane, this lane has NO spool twin to stamp when the report does not land'). The failure branch is at :2664-2686.

REVISIONS TO THE RECORDED HYPOTHESIS:
1. 'No spool/outbox/retry path exists on that route' is wrong as stated. The durable outbox EXISTS, is fsync-backed, has stable ids, gapless per-emitter sequences and a signed server ack (internal/evidencespool/spool.go, types.go, delivery.go). The PROMPT lane already implements the precise pattern the tool lane needs: `directReportLanded` set true only on a 2xx (ai_handlers.go:1459, 1498) and the twin emitted only when it is false (:1599). What is missing on the tool lane is the emitter plus the identity that makes a twin safe.
2. NEW: the PROMPT lane already has the duplicate bug the brief only anticipates for a tool-lane fix. On a committed-but-slow prompt/check, `directReportLanded` stays false, `emitPromptHookEvent` spools a twin with a fresh spool UUID, the ingest writes it as a second row with a different `client_event_id`, and one governed prompt becomes two rows. The code comment at :1573-1587 documents the duplicate as a solved problem - it is solved only for the fast path. So the idempotency work below closes a LIVE duplicate in the prompt lane, not just a hypothetical one in the tool lane.
3. NEW AND MORE SERIOUS: `evidence.durable-delivery = degraded` has a head-of-line amplifier. On a terminal (4xx) batch response `RunDelivery` RETAINS the whole batch and retries at max backoff forever (internal/evidencespool/delivery.go:47-56 - `isRetryable(err)` false => `backoff = options.MaxBackoff`, events never deleted), and `Pending` always returns the OLDEST events first (spool.go:216-227). ONE permanently-rejected event at the head of the WAL wedges the entire durable evidence lane for that endpoint until the 1,000,000-event safety bound (spool.go:33) refuses new enqueues. `Health()` reports `degraded` whenever the last attempt errored (spool.go:353-366). Routing MORE event types into that lane before per-item tolerance exists would widen a permanent-outage exposure - hence the dependency on F25.
4. The brief's rejection of a warmed transport is CORRECT and now explained: ai_prompt.go:944 sets no private Transport, so every post already rides the package-level `http.DefaultTransport` connection pool. There was never a cold transport to warm.

### Fix

ONE change closes the whole finding, and it closes the prompt-lane duplicate for free: give every synchronous governance decision a client-minted v4 UUID identity, honour that identity as the idempotency key on the server, and emit the durable twin under the SAME id when the synchronous report does not land.

WHY THIS IS THE CLEAN ONE:
- It reuses the column, the unique index, the hash coverage and the duplicate-tolerant ack semantics that are ALREADY built and already proven on the spool path. No new dedupe table, no new key derivation, no new state machine.
- It makes the ambiguous case decidable in exactly one place: the database. If the server committed, the twin is absorbed as a duplicate and the row keeps the reconciliation the synchronous append stamped. If it did not, the twin IS the row and carries `backendReconciliation=unavailable`. There is never a third state and never two rows.
- It does NOT touch the 1500ms budget, add attempts, or warm a transport. The interactive path stays fast; loss simply stops being possible.

RECONCILIATION SEMANTICS FOR THE CONSOLE (the honesty question the brief asks). Do not invent a 'delivery unknown' badge. The endpoint's honest statement is the existing, already-allowlisted `backendReconciliation` value (Installers internal/daemon/evidence_delivery.go:71; surfaced by AiQueryService.safeMetadata, pinned by ai-query.safe-metadata.backend-reconciliation.spec.ts). Its meaning is precise and must not drift: it answers 'what did the control plane contribute to THIS decision', not 'did the record arrive'. After this fix:
  - synchronous post landed -> row exists once, `backendReconciliation` = applied/confirmed. Delivery is proven by the row's own existence.
  - synchronous post failed, twin delivered -> row exists once, `backendReconciliation=unavailable`. The console renders the enforcement normally and states, in the existing honest register, that the endpoint enforced locally and the control plane did not answer. That is TRUE and is not a delivery caveat.
  - synchronous post failed AND the twin has not drained yet -> the row does not exist yet. It is not misreported; it is absent, and the endpoint's own posture surface already reports spool depth and `evidence.durable-delivery` health. Absence-with-a-named-cause is the product's existing discipline; do not add a speculative placeholder row.
Nothing here makes an honest negative look positive: the fix removes the loss, it does not relabel it.

EXPLICITLY OUT OF SCOPE (already rejected, now explained rather than merely refused): raising `aiInteractiveTimeout`, raising `aiInteractiveMaxAttempts`, and a warmed HTTP transport (ai_prompt.go:944 already uses the shared DefaultTransport pool - there is no cold transport).

A SEPARATE, NON-BLOCKING OBSERVATION worth recording rather than fixing here: the per-org `pg_advisory_xact_lock` is the latency source. Reducing it (per-endpoint sub-chains, or moving the chain-append off the synchronous response path) would cut the 26/136 timeout rate at source. That is a larger change with real tamper-evidence consequences and must not be bundled in; the fix above makes the timeouts harmless regardless.

### Root cause

Mechanism confirmed at both pinned sites, with the predicate sharpened and one design-level revision.

PRODUCER. `toolHoldApprovalTTL = 15 * time.Minute` (Installers internal/daemon/ai_tool_hold_approval.go:64). `createToolHoldApproval` sets `binding.CreatedAt = time.Now().UTC()` and `binding.ExpiresAt = binding.CreatedAt.Add(toolHoldApprovalTTL)` (:361-362), then puts `ExpiresAt: binding.ExpiresAt.Format(time.RFC3339Nano)` on the wire (:377). What crosses the network is an ABSOLUTE INSTANT DERIVED FROM THE ENDPOINT'S CLOCK.

CONSUMER. `MAX_DELEGATED_APPROVAL_TTL_MS = 15 * 60_000` (Backend src/ai-governance/services/ai-delegated-approval-authority.service.ts:30). `normalizeCreate` rejects at :437-439: `if (expiresAt.getTime() - Date.now() > MAX_DELEGATED_APPROVAL_TTL_MS) throw new BadRequestException('expiresAt exceeds the 900-second delegated approval limit')`.

THE PREDICATE, WRITTEN OUT. The server evaluates (T_client_now + 900s) - T_server_now > 900s, i.e. skew > 0, where skew = T_client_now - T_server_now at parse time. Network+queue latency L pushes T_server_now later, so the request survives only when skew < L. There is no positive tolerance at all - the contract requires the endpoint clock to be BEHIND the server clock by more than the round-trip. A correctly NTP-disciplined endpoint that is a few hundred milliseconds fast fails 100% of the time, which is precisely the observed 5-for-5.

PERMANENCE. On the 400 the goroutine never reaches `s.saveToolHold` - the local record is written ONLY inside `if err == nil && res != nil && res.RequestID != ""` (:394-402). So no local record exists, `resolveToolHoldApproval` (:253-269) finds nothing on the next identical hold, calls create again, and 400s again. The `unactionable` state is permanent for that binding and for every future one, not a transient per-attempt failure. Every TOOL_CALL_HELD the console shows carries `approvalState=unactionable` (stamped at ai_ingress.go:518-521, :586) and can never be cleared by anyone.

POSITIVE CONTROL that isolates the defect to this lane: the proxy lane (`ai_pending_action.go`) uses a 5-minute TTL, documented at ai_tool_hold_approval.go:61-63. 300s plus plausible skew is far under the 900s ceiling, so that lane's approval rows are created normally - which is why the delegated-approval tables are non-empty in general while the tool-hold arm is dead.

REVISION TO THE RECORDED FIX DIRECTION. The writeup (and the wave-2 note 'backend uses >= with a small grace') frames this as `>` vs `>=`. That framing is WRONG and a `>=` patch fixes nothing: the failing value is STRICTLY greater than the ceiling, so relaxing the comparison at the boundary changes no observed outcome. The real defect is that a CLIENT-SUPPLIED ABSOLUTE INSTANT is bounded against SERVER time by a ceiling equal to the requested duration. Any tolerance constant is a band-aid on a duration contract expressed as an instant. The brief's own closing question - 'should the ceiling be evaluated against server time rather than a client-supplied absolute expiry at all' - is the correct instinct and is the answer below.

SECOND, SILENT INSTANCE OF THE SAME ASSUMPTION. Even on success the agent never reads the authoritative expiry: the response type already carries it (`DelegatedApprovalEndpointResponse.ExpiresAt`, Installers internal/core/backend/delegated_approval.go:44-48, populated from Backend ai-delegated-approval.controller.ts:269) but `createToolHoldApproval` saves its OWN `binding` (:398-402), and `answerExistingToolHold` then expires the hold against that client-clock value (:289).
