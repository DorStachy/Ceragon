## F39 - navBlockRules=0 is a structural telemetry lie (worker-lifetime state beaconed before refresh), and the nav-block truth is never projected to the console at all

- **Severity**: HIGH - HIGH stands, for a different reason than recorded. Navigation blocking IS enforcing (the DeepSeek proof is real and, since deepseek has no content script, can only have come from DNR), so this is not a live enforcement gap. It is HIGH because the product's only measurement of that enforcement is structurally dead: the console renders every endpoint 'Active' green on evidence it never received; a genuine disarm — including the loopback-downgrade path the now-inert D100 ratchet exists to stop — would be invisible; and the 20-vs-0 discrepancy cannot be resolved by any customer using the product. A security control whose armed state cannot be observed is one silent regression away from being absent.
- **Side**: multi   **Effort**: L   **Root cause verdict**: REVISED

### Root cause

The 20-entry blocklist DOES translate into extension navigation-block rules; the beacon cannot report it. Three distinct defects, none of which is the one recorded in FINDINGS.

(1) TELEMETRY (the observed 20-vs-0). navBlockState is a plain module-scope object in the MV3 service worker (background.js:137-143, initialised {ruleCount:0, providers:[], lastRefreshedAt:null, lastFailureReason:null, trustedFloor:null}). The health alarm fires every 4 minutes (HEALTH_PERIOD_MIN, background.js:100) and its handler runs `void sendHealthBeacon(); void fetchPolicy();` in that order (background.js:888-892). sendHealthBeacon builds the whole beacon synchronously from those variables (background.js:832-845) before awaiting anything. An MV3 worker is evicted after ~30s idle, so a 4-minute alarm always wakes a FRESH module: the beacon is built from the initial zero values, and only afterwards does fetchPolicy -> refreshBlockRules install rules and set the state. The endpoint therefore reports navBlockRules=0 navBlockFailure="" on EVERY cycle by construction — and can never report a failure reason either, because every recordNavBlockFailure() call also happens after the beacon was already built. chrome.declarativeNetRequest DYNAMIC rules are persisted by Chrome across worker restarts and browser restarts, so the rules installed on the previous wake are still enforcing while the beacon says zero.

This reconciles the counter-evidence exactly. manifest.json registers content_scripts on only 9 URL patterns (the 6 composer providers) while host_permissions covers 33; the 12 named-web-app keys (deepseek, qwen, kimi, manus, zhipu, mistral, grok, meta-ai, you, huggingchat, character-ai, pi) have NO content script, so a DNR main_frame redirect is the ONLY mechanism that could have blocked DeepSeek. 'DeepSeek block PROVEN LIVE' is therefore positive proof that rules WERE installed while the beacon reported 0. This is a misleading-telemetry finding, not a nav-block regression.

(2) READ PATH. Even a correct navBlock reaches nobody. The daemon carries it into endpoint-inventory metadata.webCoverage.navBlock (browser_health.go:206-218) and logs it (browser_health.go:161-175), but the Backend web-coverage read model destructures ONLY policyAgeMs and drift (ai-query.service.ts:2645-2665); `navBlock` occurs nowhere else in Backend src and nowhere in the Frontend tree. The D10 'observable surface for the tier' terminates in a log line and an unread JSON blob.

(3) HONESTY INVERSION (the customer-visible cost). Frontend coverage-section.tsx:917-924 webGuardState(): !online => Missing; drifted => Degraded; policyAgeMs != null && > 1h => Stale; else Active. Because the beacon structurally OMITS policyAgeMs (health-beacon.js:123-127 requires fetchedAt>0, and lastPolicyFetchedAt is 0 on every wake) and reports no adapters (adapterSamples is empty on a fresh wake), every online endpoint renders 'Active' in success-green with zero evidence of policy freshness or of a single installed block rule.

(4) SECURITY SIDE-EFFECT. The D100 anti-disarm ratchet keeps its floor in the same ephemeral memory (navBlockState.trustedFloor, background.js:142; consumed at :664-676). It is null on every worker wake, so the first refresh of every wake is unratcheted: a tier-2 LOOPBACK_UNSIGNED body with providers.blocked=[] would remove every rule (refreshBlockRules :687-694 removes the owned id range and adds nothing), and the constant-zero beacon makes that real disarm indistinguishable from today's noise.

(5) VOCABULARY. 5 of the 20 blocked keys (cursor, windsurf, github-copilot, cline, gemini-cli) are AI_TOOL_PROVIDER_KEYS, not browser-navigable; buildBlockRules silently skips unknown keys (blockhosts.js:116-117). 15 of the 20 are nav-blockable (PROVIDER_BLOCK_HOSTS has 18 keys; `github` covers copilot.microsoft.com and github.com/copilot). Nothing states which 5 are not browser-enforceable, so '20 blocked' reads as 20 browser blocks.

### Fix

Report MEASURED state, not worker-lifetime intent, and project it to a customer surface.

A. The DNR engine becomes the authority for the two facts it can answer. In sendHealthBeacon, read chrome.declarativeNetRequest.getDynamicRules(), keep the ids ownsBlockRuleId() accepts, derive ruleCount from that list and `providers` from each surviving rule's redirect-URL `provider` query parameter (buildBlockRules already stamps it, blockhosts.js:120-123). Restart-proof by construction, because the rules themselves are what persist.

B. Everything the engine cannot answer becomes PERSISTED, not remembered. One chrome.storage.local record ('devoid.webguard.health') holding lastRefreshedAt, lastFailureReason, trustedFloor, lastPolicyFetchedAt, lastVerifiedPolicy, lastReceiptRelay; written whenever refreshBlockRules/recordNavBlockFailure/rememberVerifiedPolicy/recordReceiptRelay run, hydrated once at worker start and awaited before the beacon is built. Persisting trustedFloor is what revives the D100 anti-disarm ratchet across worker eviction — the same edit closes defect (4).

C. Order the alarm: refresh first (bounded 5s), beacon second. The bound is free: the alarm is every 4 min and the daemon's freshness window is 15 min (browserHealthFreshWindow, browser_health.go:26) — about three cycles of headroom.

D. Say what is NOT enforceable. The beacon gains navBlock.unsupportedProviders (blocked keys with no PROVIDER_BLOCK_HOSTS entry) so the console can state '5 of 20 blocked providers are not browser-enforceable (governed on the CLI/IDE lane)' instead of implying browser coverage for cursor/windsurf/cline/gemini-cli/github-copilot.

E. Project it. Backend web-coverage carries navBlock through; Frontend renders it and STOPS rendering unknown as Active: absent navBlock => 'Not reported' (neutral), measured ruleCount 0 while the policy blocks >=1 browser-enforceable provider => 'Blocks not armed' (critical), armed => 'Active — N provider(s) blocked'.

One mechanism (A+B) also revives the other structurally-absent beacon fields (policyAgeMs, the VERIFIED policy identity block, receiptRelay), which is the delivery vehicle F40 needs.

### Rejected alternatives

- Just reorder the alarm to refresh-then-beacon and keep in-memory state. Rejected: it hides the defect instead of removing it — any refresh failure (native host absent AND loopback token missing, the exact production shape) would still beacon ruleCount 0 while persisted DNR rules keep enforcing, so armed and disarmed stay indistinguishable. Ordering is a supporting change, never the fix.
- Persist navBlockState in chrome.storage.session. Rejected: session storage dies with the browser session, so a browser restart reproduces the same false zero — and DNR dynamic rules survive a browser restart, which is precisely the window that must stay reportable.
- Have the daemon infer the armed state from the policy it served (it knows providers.blocked). Rejected: that is reporting INTENT as endpoint state, the original D10 defect the navBlock block was created to fix.
- Drop navBlockRules from the beacon as noisy telemetry. Rejected: for the 12 named web apps there is no content script at all, so the DNR rule count is the ONLY evidence that the block tier exists on that endpoint.
- Add cursor/windsurf/cline/gemini-cli/github-copilot hosts to PROVIDER_BLOCK_HOSTS so all 20 keys match. Rejected: those are IDE/CLI tools governed on the hook and wire lanes; inventing web hosts for them would manufacture coverage claims. The honest fix is to REPORT them as not browser-enforceable.

### Risks

Old extension (0.5.13) against the new Backend: no navBlock in metadata -> navBlockRuleCount/navBlockArmed null -> the console MUST render 'Not reported', never 'not armed'; asserted by test rather than assumed, because rendering absence as a defect is the mirror image of today's bug. New extension against today's Backend: the extra beacon keys ride endpoint-inventory item metadata, validated as a free-form @IsObject with per-item-tolerant ingest (endpoint-inventory-batch.dto.ts:115-122), so there is no 400 risk; the fields are simply invisible until Backend ships. Deploy order is therefore Backend-then-agent for VISIBILITY, and neither order can break the wire. RuleCount int -> *int in the daemon struct: a beacon from an older extension omits ruleCount (nil), which must stay distinguishable from 'NavBlock absent entirely' (the contract documented at browser_health.go:47-53); its existing test must be extended, not replaced. Reading getDynamicRules() per beacon adds one async chrome call every 4 minutes — negligible, and it is already called in refreshBlockRules and verifyNavBlockPage. Persisting trustedFloor makes the D100 ratchet real for the first time: on a box where the native host is broken and only the loopback lane works, a legitimate UNBLOCK will now be refused until the host is repaired. That is the intended posture (the refusal names itself in lastFailureReason, which is now actually reportable) but it must be in the release note. The Frontend ladder change is user-visible: endpoints that read 'Active' today will read 'Not reported' until the fixed extension ships — that is the honest state and must not be softened.

B. GRACE VS GONE, decided on-box and cheaply. A window marker (~/.devoid/ai-hook-ungoverned.json, same discipline as the spool: bounded, best-effort, never affects the verdict) holds {sinceMs, count, lastMs}. The first ungoverned invocation opens it, each subsequent one increments, the first governed decision CLOSES it and appends a closing record. Classification: age <= 60s => BLIP (a service restart); age > 60s => GONE. 60s is chosen because the daemon heartbeat interval is 60s, so a window longer than one heartbeat is one the server will also see.

C. VISIBILITY PROPORTIONAL TO THE CLASSIFICATION. BLIP keeps today's single stderr line. Never on stdout — that is the hook's protocol channel.

D. SEPARATE 'not answering' FROM 'answering wrong'. askDaemonToolDecision/askDaemonPromptCheck return a classified outcome (ok | unreachable | status | decode) instead of a bare bool, mirroring the shim's own daemonReachable discipline. Both still proceed today, but they are counted and alerted separately, because a 5xx-ing daemon is a broken governor rather than a restart.

E. OWNER DECISION, with the numbers stated. Today: the ungoverned window equals the full daemon-down duration; nothing on-box records it; the server notices absence only after 300-360s and only for capability-latched endpoints; every proceed is counted as governed. OPTION A (this spec, recommended, ships now): availability cost ZERO — no decision changes; detection: the count reaches the backend within <=60s of the daemon returning (the heartbeat that drains the spool), the HOOK_UNDECIDABLE row records when and how many, and the developer is told during the window. OPTION B (fail closed after the 60s grace, gating checkpoints only): cost = every tool call and prompt denied while the daemon is down beyond 60s; a service restart/upgrade is seconds, so the only cases beyond grace are a crash with no restart and a deliberately stopped service — and the 2026-07-31 precedent shows a hard block in that state produced an uninstall. Not recommended before Option A has produced a MEASURED distribution of window durations; Option A is what makes that measurement exist. OPTION C (fail closed for the 'daemon-error' sub-case only): near-zero availability cost (a daemon answering 5xx is already broken and self-heal restarts it) with a real security gain, because that state cannot be caused by a restart. Recommended as the follow-up once Option A shows the daemon-error rate is as low as expected.
