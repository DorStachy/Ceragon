Reading: exit 1 on the two ACCEPTED shapes means both binaries reached runLauncher and tried to
exec the absent devoid.exe. Exit 2 on the rejected shapes means childArgs rejected them
identically. `service` is exit 2 on BOTH — the marker argument is not a detector and a process
SCM did not start is still refused.

WHY THE NEW CODE PATH CANNOT BE REACHED ON AN ENDPOINT (three independent reasons):

  1. svc.IsWindowsService() is the only detector. Its implementation
     (golang.org/x/sys@v0.38.0/windows/svc/security.go:66-98) returns true only when the
     process's OWN parent has SessionID == 0 AND is named services.exe. The fleet launches this
     binary from an ONSTART scheduled task, whose parent is the Task Scheduler's svchost.exe —
     it fails the name test. No argument, environment variable or registry value participates.
  2. ANY detector error takes the launcher path (chooseStartupMode).
  3. Even a wrong "yes" cannot stop the daemon: if svc.Run returns
     ERROR_FAILED_SERVICE_CONTROLLER_CONNECT (1063), main() falls through to runLauncher instead
     of exiting. This is defence in depth beyond what the task asked for, and it exists because
     the failure it covers is a silent fleet-wide daemon outage.

5. THE PIDFILE DISCOVERY STEP — the premise does not hold, and it does not need to
================================================================================

The task asks whether a service-launched SYSTEM daemon and a task-launched SYSTEM daemon resolve
secPaths.DaemonPIDPath to the same file, and says the whole no-second-listener argument rests on it.

STATIC ANSWER: security.DefaultPaths (internal/security/paths.go:27-46) computes
  DaemonPIDPath = os.UserHomeDir() + "/.devoid/daemon.pid"
and on Windows os.UserHomeDir() reads %USERPROFILE%. Both launch contexts run as LocalSystem, whose
profile is C:\Windows\system32\config\systemprofile, and a Windows service inherits the SYSTEM
environment block just as an ONSTART SYSTEM task does. So they should resolve to the same file.

NOT EXERCISED: proving it needs a process under LocalSystem in each context. The suggested method
(psexec -s) INSTALLS A WINDOWS SERVICE, which this task is explicitly forbidden from doing on this
machine, and registering the real service is Task 3. Left for Task 3, which is registering the
service anyway.

MORE IMPORTANT: the premise that the argument rests on the pidfile is wrong, and the source says
so. internal/daemon/pidfile.go:24-31 — "The authoritative single-instance guard remains
net.Listen(127.0.0.1:19280) in RunWithContext; this check merely gives a clean 'already running'
message"; and again at :98 — "net.Listen(:19280) is the real mutex for a genuine double-start."
The port bind is process- and profile-agnostic and cannot diverge between launch contexts, so
even a diverged pidfile path could not produce two listeners. The supervisor adds two more
barriers above it: it never spawns while a healthy daemon answers, and never spawns into a held
port. A Global\ named mutex is therefore not required by this task.
