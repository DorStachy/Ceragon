2. THE SECOND EXIT — KILL WITH THE SCHEDULED TASK DELETED
==============================================================================

The wave's second exit repeats the kill with the 'Devoid Daemon' scheduled
task deleted first. Today that is unrecoverable until reboot, because the
in-process watchdog cannot run while the process is dead.

The harness above ALREADY models exactly that case and it is not a separate
run. Nothing in it registers, reads or repairs a scheduled task: the only
thing that brings the daemon back across all ten cycles is the supervisor's
own spawn, attributed by a daemon_supervisor_restarted event per cycle. A
deleted task changes nothing about that path.

What a deleted task DOES change is who starts the daemon at the next boot, and
that is a property of the SERVICE REGISTRATION, not of this loop. It stays
NOT EXERCISED with the rest of the VM run.

3. THE GAP W2 T3 NAMED AND THIS TASK DID NOT CLOSE
==============================================================================

A wedged-but-running OWNED child is recovered by neither mechanism. The
supervisor holds Wait for as long as it lasts, so the supervisor process
stays healthy and the SCM's failure actions never fire.

Measured directly against daemonsupervise.NextSupervisorAction (throwaway
probe, not committed):

  failures=2       restarts=0    ChildOwned=true -> Wait  (unhealthy 30s)
  failures=10      restarts=5    ChildOwned=true -> Wait  (unhealthy 2m30s)
  failures=100     restarts=500  ChildOwned=true -> Wait  (unhealthy 25m0s)
  failures=1000    restarts=500  ChildOwned=true -> Wait  (unhealthy 4h10m0s)
  failures=100000  restarts=500  ChildOwned=true -> Wait  (unhealthy 416h40m0s)
  owned child ALSO holding the port          -> GiveUpAndReport

It is unbounded by construction: the arm is 'if s.ChildOwned { return Wait }'
with no failure-count condition, and the loop clears ChildOwned only when the
child process EXITS. A child that is alive and not answering never does.

It was NOT fixed here, deliberately. Two pins merged with W2 T3 assert the
current behaviour as intended:

  TestSupervisor_WaitsWhileItsOwnChildIsStillStarting  asserts Wait for
    ConsecutiveFailures 1..20 and any restart budget;
  TestSupervisor_DoesNotSpawnIntoAHeldPort             asserts GiveUpAndReport
    for a held port INCLUDING ChildOwned=true.

Closing the gap needs a new SupervisorAction and both pins rewritten. The wave
rule is explicit that a task blocked by an existing pin is the wrong task, so
this is reported rather than improvised. It wants its own task.

5. THE FOUR STATES ON THE DOCTOR SURFACE
==============================================================================

One row, 'Daemon service', read from the daemon's serviceSupervision block.
There is no local fallback and that is by design: the descriptor W2 T3 applies
withholds SERVICE_QUERY_CONFIG from INTERACTIVE, so an unelevated
'sc qc devoid-daemon' is refused. The daemon runs as LocalSystem and is the
only reader that can answer.

  could not determine     FAIL       could not be verified (the daemon could
                                     not read the service: <sc error>)
  no daemon reached       FAIL       could not be verified (daemon unreachable;
                                     an unelevated CLI cannot read the service
                                     configuration)
  NOT REGISTERED          unverified no devoid-daemon service is registered --
                                     recovery on this endpoint is the ONSTART
                                     task's own restart-on-failure, which
                                     cannot run while the daemon is dead. A
                                     service is registered by the installer,
                                     not by this endpoint.
  registered, misconfigured FAIL     <the daemon's own reason> (the daemon
                                     repairs this on its next reconcile)
  registered, NOT running   PASS     registered, not running -- the SCM starts
                                     it at the next boot and restarts it on
                                     failure thereafter
  registered AND running    PASS     registered and running -- the SCM restarts
                                     the daemon if it dies

'not registered' is EVERY endpoint in the field today, so it is neither a
failure nor a green tick. It takes the scoreboard's third state, which is
COUNTED, suppresses the all-clear line, and prints on the --quiet surface that
install.ps1 and install.sh echo. It is not the old neutral row and it is not
an 'unknown': an undetermined service still FAILS this row.
