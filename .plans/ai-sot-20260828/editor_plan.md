### N1 — `rm -rf ~/anything` is a hard block no administrator can lift *(the top item; the document does not mention it at all)*

The most customer-visible fact about the product today. Add as a fifth walkthrough in §4, and a cross-reference from §7.2 and §17.

> **A developer clears a cache directory.** `rm -rf ~/.npm/_cacache`, or `rm -rf $HOME/.cache/pip`, or `rm -rf $HOME/projects/scratch`. The `PreToolUse` hook fires, the shipped `destructive-rm` rule matches — its broad-target alternation accepts `~` followed by any path and `$HOME` followed by any path — and the class is a malicious-floor member at minimum disposition `block`. The tool call is refused. Because the floor now holds on the read path, an administrator who sets `destructive-rm` to `warn` in the console will see the value stored, get a 200 back, and be served `block` on the very next policy pull. **There is no tenant configuration that makes this command run.** `rm -rf ./build` and `rm -rf /tmp/mybuild` are correctly unaffected. This is the likeliest reason a developer uninstalls the agent — the exact failure §2 says the design exists to avoid.

Evidence, verified by me at `origin/main`: `Installers/internal/toolrisk/toolrisk.go:121-122`, alternation `(?:/\s*$|/\s+|/\*|~(?:/\S*)?|\$HOME\b|\.{1,2}\s*$|\*\s*$|/(?:etc|usr|var|bin|…)\b)` — the `~(?:/\S*)?` and `\$HOME\b` branches match any path under either. Floor membership: `Backend/src/ai-security-policy/ai-malicious-floor.ts:155` `destructive('destructive-rm')`, `minimumDisposition: 'block'` (:104-109). Non-relaxable: `ai-security-policy.service.ts:2198`. Stored D4 tier is `warn` (constants.ts:1238), so console and wire disagree by construction.
**Honesty note for the writer:** the pattern match is confirmed by reading the shipped regex; the end-to-end block has **not** been observed on a live endpoint and there is no register entry for it. Write it as a structural fact plus a stated consequence, not as PROVEN LIVE.

### N2 — A new §3.4: "What an administrator cannot change"

Part I currently tells a CEO that the customer's administrator sets the policy (§1) and that the coarse gate outranks everything (§3.2). Both now have a named exception, and there is no language anywhere in the document for the support ticket it produces.

> ### 3.4 What an administrator cannot change
>
> **One floor outranks the administrator entirely.** Thirty-seven detector classes sit on a *malicious floor*: thirteen destructive-execution classes and eight self-tampering classes pinned at `block`, two credential-read tool classes at `block`, ten credential DLP classes at `redact`, and four injection-that-acts prompt classes at `warn`. Since 2026-08-27 the floor is applied as the unconditional first statement of every effective-policy assembly, which is the only way to build a wire payload.
>
> An administrator may store a weaker value. The console will show it, the write returns 200, and the endpoint is served the floored value on the next pull. The stored row is deliberately **not** rewritten — so the console keeps showing what the human actually chose — and a server-log warning names every raise. This is intentional: being the first statement is what makes the floor unbypassable rather than a property of whichever caller remembered to call it. But it means "the customer's administrator sets the policy" has a named exception, and `destructive-rm` (§4) is the one customers will find first. **Anyone answering a support ticket that begins "I set it to warn and it still blocks" should start here.**

### N3 — GAP: an uppercase extension walks past every shim gate

*(Verified by me at `origin/main`: `cmd/devoid/main.go:242-247`, :203, :4648, :4778-4781.)*

> **GAP — an uppercase extension walks past every shim gate.** Dispatch normalises `argv[0]` by stripping `.exe`/`.cmd`/`.bat` and then lowercasing, and the strip is case-sensitive. `CLAUDE.EXE` therefore normalises to `claude.exe`, matches no dispatch branch, and is handed to the real binary as an unrecognised tool — no surface gate, no provider deny-list, no agent allowlist, no transport injection, no bypass-flag strip, no plugin gate. Windows resolves the name case-insensitively, so it runs. It needs no privilege, no config edit and no tampering. Nothing on any status surface would report it, because the shim process the reporting counts never starts. The fix is one line — lowercase first, then strip — and until it lands the shim lane's guarantee is "governed unless the developer types the extension in capitals".

Add a matching row to §13.1 (fails open) and to §17.

### N5 — When coverage begins is not when the installer finishes *(move + extend)*

Move §5.2's "What a fresh install does NOT do" paragraph up to §3.3, directly under the coverage table, and add the measured numbers:

### N6 — The unanswered warn *(new walkthrough for §4)*

> **A developer's prompt trips a warn, and nobody is at the keyboard.** A warn is not a soft block — on the wire it becomes an interactive hold, released only by a single-use, digest-bound allow-once. The developer gets 30 seconds to answer, inside a 40-second hold ceiling, inside the host's 60-second hook timeout. If the session is not interactive — a CI job, a headless agent, an IDE-hosted client that never launched through our shim — there is nobody to ask, and on the Anthropic lane the warn **downgrades to allow**: the prompt is sent and an audit record stamped `warn_degraded_noninteractive` is written. The single exception is a conclusive secret, which becomes a block. The same policy therefore produces opposite outcomes depending on whether a terminal is attached, and the permissive one is the default. The Codex wire lane has no such degrade.
